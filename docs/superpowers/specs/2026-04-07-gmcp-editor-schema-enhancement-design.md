# GMCP Editor Schema Enhancement — Design Spec

## Problem

The `Sentience.Editor.Open` message sends a field schema generated by running
each editor tab's show function in capture mode. However, several categories of
fields bypass the `olc_display_*` capture system entirely:

1. **Type data fields** — `oedit_show_type_tab` calls `oedit_show_type_data()`
   which renders raw text to a buffer. The 32 object types we just staged in
   Phase 3 produce zero schema output for the web client.

2. **List fields** — Affects, spells, catalysts, quests, and scripts are rendered
   with raw `add_buf()` / `snprintf()` calls. `olc_display_list()` returns
   immediately in capture mode.

3. **Non-flag enum fields** — Many fields with constrained choices (weapon class,
   armor type, sector type, size, sex) use `olc_display_string()` or
   `olc_display_number()` instead of `olc_display_type()`, so they appear as
   plain text/numbers without valid options.

4. **No targeted schema updates** — When structural changes occur (addtype,
   removetype, commit), the web client's schema becomes stale with no way to
   update it short of re-entering the editor.

The web client cannot render proper forms for type-specific data, list-based
content, or provide dropdown selectors for enum fields.

## Solution

Four coordinated changes to make all editor schemas fully self-describing:

### A. Type Schema Functions

Add a third function to the oedit type dispatch table:

```c
typedef json_t *(*oedit_type_schema_fn)(const OBJ_INDEX_DATA *pObj);
```

Each of the 32 types implements a schema function that returns a JSON array of
field descriptors matching the `Editor.Open` format:

```json
[
  {
    "label": "Class:",
    "command": "typedata/weapon/class",
    "type": "enum",
    "value": "sword",
    "options": ["exotic","sword","dagger","spear","mace","axe","flail","whip","polearm"]
  },
  {
    "label": "Flags:",
    "command": "typedata/weapon/flags",
    "type": "flags",
    "value": "flaming",
    "options": ["flaming","frost","vampiric","sharp","vorpal","two_hands",...]
  },
  {
    "label": "Dice:",
    "command": "typedata/weapon/dice",
    "type": "dice",
    "value": "3d6+2"
  }
]
```

The `command` field uses the `typedata/typename/field` path matching the
`Editor.Set` protocol — the web client sends the same path to modify the field.

The type tab's capture-mode path iterates the object's active types, calls each
type's `schema_fn`, and groups results by type name with section markers.

A public function `oedit_type_schema()` parallels the existing
`oedit_apply_typedata()` and `oedit_serialize_typedata()`.

### B. List Schema in Capture Mode

The affects, scripts, and related tabs currently write raw text in capture mode.
Add structured capture output for list-based content:

For each list section (affects, immunities, spells, catalysts, quests, scripts),
emit a field descriptor of type `"list"` with:

```json
{
  "label": "Affects",
  "command": "affects",
  "type": "list",
  "item_type": "affect",
  "items": [
    {"index": 0, "where": "object", "location": "strength", "modifier": 10, "random": 0},
    {"index": 1, "where": "object", "location": "dexterity", "modifier": 5, "random": 0}
  ],
  "add_command": "addaffect",
  "del_command": "delaffect",
  "item_schema": [
    {"field": "where", "type": "enum", "options": ["object","immune","resist","vuln"]},
    {"field": "location", "type": "enum", "options": ["strength","dexterity","intelligence",...]},
    {"field": "modifier", "type": "int"},
    {"field": "random", "type": "int", "min": 0, "max": 100}
  ]
}
```

This gives the web client:
- Current items with their data
- Commands to add/remove items
- Schema for the add form (what fields, what options)

Each editor's list-based show function gains a capture-mode path that builds
these descriptors. The item data comes from iterating the live data structures,
same as the text renderer does.

### C. `Sentience.Editor.Schema.Update` Message

New server → client GMCP message for targeted schema updates:

```json
{
  "entity_id": "obj:5#3010",
  "updates": [
    {
      "tab": "Type",
      "action": "replace",
      "fields": [ ...full fields array for the Type tab... ]
    }
  ]
}
```

**Fields:**

| Field | Type | Description |
|-------|------|-------------|
| `entity_id` | string | Entity being edited |
| `updates` | array | Array of tab update objects |
| `updates[].tab` | string | Tab name to update |
| `updates[].action` | string | `"replace"` — replaces the full fields array |
| `updates[].fields` | array | New field descriptors for this tab |

**Triggers:**

| Event | Tab Updated | When |
|-------|-------------|------|
| `addtype` stages new type | Type | After staging the +type change |
| `removetype` stages type removal | Type | After staging the -type change |
| `commit` applies structural changes | Affected tabs | After successful commit |
| `revert` removes structural changes | Affected tabs | After revert changes schema |

The Type tab is the primary consumer since its available fields depend on which
types are allocated. The Affects tab may also need refresh after commit if list
operations changed the item count.

**Implementation:**

Add `gmcp_editor_send_schema_update()` in `gmcp_editor.c`:

```c
void gmcp_editor_send_schema_update(descriptor_t *d,
    const char *entity_id, const char *tab_name,
    json_t *fields);
```

Call sites:
- `oedit_addtype` / `oedit_removetype` — after staging, regenerate Type tab
  schema and send update
- `olc_changeset_commit` wrapper — if commit touched structural fields, resend
  affected tab schemas
- `olc_staged_cmd_revert` — if reverting structural changes, resend tab schema

### D. Options Enrichment for Non-Flag Fields

The `olc_display_type()` function already captures as `"enum"` with options.
Many editor show functions use `olc_display_string()` or `olc_display_number()`
for fields that actually have constrained choices.

Convert these to `olc_display_type()` (which takes a `flag_type *table`) in all
4 editors' show functions. This is a mechanical change — find every field where
a `flag_value()` table exists but the display uses `string`/`number`, and switch
to `olc_display_type()`.

Examples across editors:

| Editor | Field | Current | Table |
|--------|-------|---------|-------|
| medit | Sex | `olc_display_string` | `sex_flags` |
| medit | Size | `olc_display_string` | `size_flags` |
| redit | Sector | `olc_display_string` | `sector_flags` |

Note: `material_type` is a struct (not a `flag_type` table) and cannot use
`olc_display_type()` directly — it needs a dedicated adapter or remains as-is.
aedit Security is a numeric range (1–9), not an enum — it stays as
`olc_display_number` with no options enrichment needed.

The type schema functions handle their own options internally (weapon_class,
armor_type, etc.) since they don't go through `olc_display_*`.

## Architecture

```
Editor.Open (existing)
  └── olc_schema_capture()
        ├── Tab show functions (existing capture paths)
        │     ├── olc_display_type() → "enum" with options ✓
        │     ├── olc_display_flags() → "flags" with options ✓
        │     ├── olc_display_string() → "string" (convert to type where applicable)
        │     └── NEW: list capture paths → "list" with items + item_schema
        └── Type tab capture path
              └── NEW: oedit_type_schema(pObj) → per-type field descriptors

Editor.Schema.Update (new)
  └── gmcp_editor_send_schema_update()
        ├── Called from addtype/removetype staging
        ├── Called from commit (structural changes)
        └── Called from revert (structural changes)
```

## Scope

**In scope:**
- Type schema functions for all 32 oedit types
- List schema capture for all list-based tabs (affects, spells, catalysts,
  quests, scripts — across editors that have them)
- `olc_display_type()` conversions across all 4 editors
- `Sentience.Editor.Schema.Update` message and triggers
- Reference doc updates

**Out of scope:**
- Web client UI changes (that's a separate repo/project)
- On-demand query protocol (schema-embedded approach chosen)
- Telnet display changes (capture paths are orthogonal)
- New editor migrations (only enhancing existing 4 editors)

## Conventions

- Type schema function naming: `{typename}_schema()` (e.g., `weapon_schema()`)
- Command paths in type schema use `typedata/{type}/{field}` format
- List field descriptors use `"type": "list"` with `item_schema` sub-array
- All new GMCP messages increment `_v` field if format changes
- Schema.Update uses same field descriptor format as Editor.Open tabs
