# Editor.Open Schema Design Spec

## Problem

When a builder enters an OLC editor, the web client receives `Editor.State` with
only the entity ID, pending changes count, and change list. It has no field
definitions—no names, types, current values, or valid options. The client cannot
render editor forms without this information.

## Solution

Add a `Sentience.Editor.Open` GMCP message sent on editor entry. It contains:

1. A tab-grouped field schema generated by running each tab's show function in
   a capture mode.
2. The existing changeset state (pending changes, draft_restored) embedded inline.

This replaces the `Editor.State` message sent on editor entry. `Editor.State`
continues to be sent for incremental changeset updates (e.g., after `Editor.Set`
or MUD commands).

## Approach: Hybrid Auto-Capture

The `olc_display_*` functions already encode field metadata: each call includes
label, command name, type (implied by which function), and current value. We add
a `capture_mode` flag to `OLC_LAYOUT_CTX`. When set, display functions append
JSON field descriptors instead of rendering text.

Constraint metadata (min/max for numbers, max_length for strings) is supplied
via small per-editor annotation arrays, merged by matching on the command name
after capture completes.

### OLC_LAYOUT_CTX Changes

Add to the existing `OLC_LAYOUT_CTX` struct in `editors/common.h`:

```c
typedef struct olc_layout_ctx {
    // ... existing fields ...
    bool         capture_mode;   // When true, capture field descriptors
    json_t      *captured_fields; // JSON array of field descriptors
    const char  *current_section; // Current section name for grouping
} OLC_LAYOUT_CTX;
```

### Capture Behavior Per Display Function

When `ctx->capture_mode` is true, each `olc_display_*` function appends a JSON
object to `ctx->captured_fields` and returns without rendering text.

| Function | Schema type | Extra fields captured |
|----------|------------|----------------------|
| `olc_display_string` | `"string"` | value (string) |
| `olc_display_number` | `"int"` | value (integer) |
| `olc_display_bool` | `"bool"` | value (boolean) |
| `olc_display_type` | `"enum"` | value (string name), options (string array from flag_table) |
| `olc_display_flags` | `"flags"` | value (string of set flags), options (string array from flag_table) |
| `olc_display_text` | `"multiline"` | value (string) |
| `olc_display_dice` | `"dice"` | value (string "XdY+Z") |
| `olc_display_vnum` | `"vnum"` | value (integer) |
| `olc_display_widevnum` | `"widevnum"` | value (string "area#vnum") |
| `olc_display_percent` | `"percent"` | value (integer raw), scale (integer) |
| `olc_display_pair` | Two field entries | Each half captured as its own field. The capture branch extracts label1/cmd1/value1 and label2/cmd2/value2 directly from the function parameters — it does not delegate to `olc_display_string()`. |
| `olc_display_section` | `"_section"` | title (string) — structural marker |
| `olc_display_infof` | `"_info"` | text (string) — read-only info line |
| `olc_display_hr` | Skipped | No capture |
| `olc_display_blank` | Skipped | No capture |
| `olc_display_table_*` | Skipped | Complex visual; not capturable as fields |
| `olc_display_list` | Skipped | Complex visual |
| `olc_display_scripts` | Skipped | Complex visual |
| `olc_display_vars` | Skipped | Complex visual |
| `olc_display_entity_list` | Skipped | Complex visual |
| `olc_display_header` | Skipped | Chrome, not data |
| `olc_display_footer` | Skipped | Chrome, not data |

### Captured Field Descriptor Format

Each field descriptor is a JSON object:

```json
{
  "label": "Room flags:",
  "command": "room",
  "type": "flags",
  "value": "dark indoors",
  "options": ["dark", "indoors", "no_mob", "private", "safe", "solitary"],
  "section": "Flags"
}
```

- `label`: Human-readable label from the display call.
- `command`: The OLC command name used to edit this field. NULL command → field
  is `"readonly": true` with no `command` key.
- `type`: One of `"string"`, `"int"`, `"bool"`, `"enum"`, `"flags"`,
  `"multiline"`, `"dice"`, `"vnum"`, `"widevnum"`, `"percent"`.
- `value`: Current value in the type's natural representation.
- `options`: (flags/enum only) Array of valid option name strings from the
  flag_type table.
- `section`: Current section name from the most recent `olc_display_section()`
  call, or NULL if no section is active.
- `readonly`: Present and `true` when the field has no command (display-only).

Structural markers (`_section`, `_info`) are included in the fields array with
type prefixed by underscore so the client can render section headings and info
text in the form layout.

### Constraint Annotations

```c
typedef struct olc_field_annotation {
    const char *command;     // Field command name to match
    int         min;         // Minimum value (INT_MIN = no minimum)
    int         max;         // Maximum value (INT_MAX = no maximum)
    int         max_length;  // Max string length (0 = no limit)
} olc_field_annotation_t;
```

Per-editor annotation arrays (NULL-terminated):

```c
// redit.c
static const olc_field_annotation_t redit_annotations[] = {
    { "heal",  .min = 0, .max = 10000 },
    { "mana",  .min = 0, .max = 10000 },
    { "move",  .min = 0, .max = 10000 },
    { NULL }
};
```

Added to `OLC_EDITOR_DEF`:

```c
const olc_field_annotation_t *annotations; // Field constraint annotations
```

After schema capture, annotations are merged by matching `command` name. If an
annotation matches, `min`, `max`, and/or `max_length` are added to the field
descriptor JSON.

### Schema Capture Orchestration

New function in `olc_display.c`:

```c
json_t *olc_schema_capture(CHAR_DATA *ch, const OLC_EDITOR_DEF *def,
                           void *entity, olc_changeset_t *cs);
```

This function:

1. Creates a capture-mode `OLC_LAYOUT_CTX`.
2. Iterates each tab in `def->tabs`, calling `tab.show_fn(ch, ctx, entity)`.
3. For each tab, collects `ctx->captured_fields` into a tab JSON object.
4. Merges annotations from `def->annotations`.
5. Returns a JSON array of tab objects.

If the editor has no tabs (`def->tabs.count == 0`), it calls `def->show_fn`
directly and produces a single tab named after the editor.

### Editor.Open GMCP Message

New functions in `gmcp_editor.c`:

```c
json_t *gmcp_editor_build_open(const char *entity_id, const char *editor_name,
    const char *editor_type, json_t *tabs, olc_changeset_t *cs,
    bool draft_restored);

void gmcp_editor_send_open(descriptor_t *d, const OLC_EDITOR_DEF *def,
    void *entity, const char *entity_id, olc_changeset_t *cs,
    bool draft_restored);
```

`gmcp_editor_send_open()` calls `olc_schema_capture()` to build the tabs array,
then `gmcp_editor_build_open()` to assemble the final message, then sends it.

### Editor Type Mapping

The `editor_type` string is derived from the `ED_*` constant:

| ED_* constant | editor_type string |
|---------------|-------------------|
| ED_ROOM | `"room"` |
| ED_MOBILE | `"mobile"` |
| ED_OBJECT | `"object"` |
| ED_AREA | `"area"` |
| Other ED_* | Lowercase of `def->name` as fallback |

### Integration Point

In `olc_editor_enter()` (editors/common/olc_editor.c), the current
`gmcp_editor_send_state()` call is replaced with `gmcp_editor_send_open()`.

`Editor.State` continues to be sent for incremental updates after field changes,
commits, and reverts.

## Testing

New test cases:

1. **Schema capture basic**: Create a mock editor with known display calls,
   verify captured JSON has correct field count, types, and values.
2. **Tab grouping**: Verify multi-tab editors produce correct tab structure.
3. **Annotation merge**: Verify min/max/max_length are merged into captured
   fields from annotation arrays.
4. **Readonly fields**: Verify NULL-command fields have `readonly: true`.
5. **Flag/enum options**: Verify flag_type table names are captured as option
   arrays.
6. **Section markers**: Verify `_section` entries appear in fields array.
7. **Editor.Open build**: Verify full message structure with entity_id, editor,
   tabs, and embedded state.

## Client Consumption

The web client receives `Editor.Open` and:

1. Reads `editor` and `editor_type` to select appropriate UI behavior.
2. Renders tabs from the `tabs[]` array.
3. For each tab, renders form fields based on `type`:
   - `string` → text input
   - `int` → number input (with min/max if present)
   - `bool` → toggle/checkbox
   - `enum` → dropdown (from options)
   - `flags` → multi-select checkboxes (from options)
   - `multiline` → textarea (opens StringEdit session)
   - `dice` → specialized dice input (XdY+Z)
   - `vnum`/`widevnum` → reference input
   - `percent` → percentage input
   - `_section` → section heading
   - `_info` → read-only info text
   - `readonly: true` → display-only, no form control
4. Editable fields send `Editor.Set` with `{"field": "<command>", "value": ...}`.
5. `state.changes[]` shows any pre-existing pending changes (e.g., from a
   restored draft).
6. Subsequent `Editor.Field` messages update individual field values in the
   local UI.
